# Repository instructions

These instructions apply to every Codex task in this repository.

## Working agreement

- Never merge a pull request. The repository owner reviews and squash-merges pull requests manually.
- Never enable auto-merge.
- Never push directly to `main` or bypass its branch protection.
- For each repository change, fetch the latest `origin/main`, create a dedicated `codex/<short-description>` branch from it, and keep unrelated work out of the branch.
- Preserve existing user changes. Stage only files that belong to the requested change.
- After implementation, run the relevant checks, create a focused conventional commit, push the branch, and open a pull request targeting `main`.
- Open the pull request as a draft while checks run. When all required checks pass, mark it ready for review and leave it open for the owner to merge.
- If checks fail, diagnose and fix them on the same branch. Do not mark the pull request ready while required checks are failing.
- End the task with the pull request URL, validation results, and an explicit statement that the pull request was not merged.

## Pull requests and releases

- Pull request titles and squash commit subjects must follow Conventional Commits.
- Use `fix:` for a backwards-compatible product fix, `feat:` for a backwards-compatible product feature, and a `!` after the relevant type (for example, `feat!:`) or a `BREAKING CHANGE:` footer for a breaking product change.
- Use `ci:`, `docs:`, `test:`, `chore:`, or `build:` for maintenance-only changes. These types must not create a product release.
- Do not change the package version, create release commits, tags, or GitHub Releases as part of a normal pull request.
- After the owner merges a product pull request, the `Version and release` workflow creates a separate version commit on `main`, adds the Git tag and GitHub Release, and triggers the versioned deployment.
- The automated release workflow is the only allowed direct writer to `main`. Do not use or modify its deploy key unless the user explicitly requests a release-infrastructure change.
- The repository supports squash merge only. Do not rebase-merge or create merge commits.

## Validation

- Use `pnpm` for dependency and script commands.
- Run `pnpm test` for code changes.
- Run `pnpm build` for application or build-related changes.
- Run `git diff --check` before committing.
- For user-interface changes, verify the affected behavior in a browser and include responsive/mobile coverage when relevant.
- Do not suppress TypeScript errors or weaken checks to make validation pass.

## Project constraints

- Use only Smithsonian Global Volcanism Program sources from `volcano.si.edu` for volcano and eruption data. Do not add sample, fabricated, or fallback volcano records.
- The application must not use a database, `localStorage`, a Service Worker, or another persistent client-side data cache. Runtime data stays in memory.
- GitHub Pages data snapshots are generated by GitHub Actions, included only in the deployment artifact, and must not be committed.
- Keep source code, comments, tests, configuration, commit messages, pull request text, and developer documentation in English.
- Polish is allowed only in user-interface translation content. The interface supports Polish and English; update both locales whenever user-facing copy changes.
- Parse remote Smithsonian data defensively. Missing or incomplete fields must not crash the application.
- Match volcanoes, eruptions, and weekly reports by GVP number first. Use conservative normalized-name matching only when an RSS entry has no GVP number.
- Do not present the weekly report as a complete list of active volcanoes.

## Definition of done

A repository change is complete only when the requested scope is implemented, relevant checks pass, the branch is pushed, and a ready-for-review pull request is open. Completion never includes merging the pull request.
